# Mady 桌面端设计审阅报告

**审阅日期**：2026-07-27
**审阅范围**：`docs/specs/desktop/` 下的 4 份文档（01-proposal.md / 02-spec.md / 03-design.md / 04-tasks.md）
**审阅方式**：对照现有 `a2ui/`、`agui/`、`server/`、`cmd/mady/` 代码实现，结合开源社区优秀实践进行交叉验证。

---

## 1. 执行摘要

桌面端设计文档整体方向正确、规格细致、审美专业，是一份高质量的启动蓝图。它充分利用了 Mady 已有的协议资产（A2UI v0.9.1、AGUI SSE、`server.Handler()`），选择 Wails v2 内嵌 + React/shadcn/ui 渲染 A2UI 的路径，与项目“克制、中庸、去繁就简”的哲学高度一致。

**但存在若干会阻塞实现的现实缺口**，主要集中在：

1. `server` 包当前没有可供桌面端直接调用的非 HTTP chat 执行入口；
2. `cmd/mady/framework.go` 的装配逻辑未导出，无法被 `desktop/` 直接复用；
3. A2UI `Dynamic` 的 wire 格式与 spec 描述不一致；
4. AGUI 事件名到 Wails 事件名的映射层被低估；
5. 一些前端工具链版本与 Wails v2 的兼容性需要先行验证。

建议在人工 Sign-off 前，先补齐这些问题清单中的“阻塞项”，并调整任务拆解让风险前置。

## 3. 合理性分析

### 3.1 桌面框架：Wails v2 是正确选择

对比开源社区 2026 年的主流方案：

| 方案 | 优劣 | 与 Mady 契合度 |
|------|------|----------------|
| **Wails v2** | Go 原生、系统 WebView、单二进制、~15MB | ★★★★★ 直接 import Go 后端，零 sidecar |
| Tauri v2 | 更小、安全模型成熟，但需 Rust 和后端 sidecar | ★★★☆ 引入新编译链，违背“克制” |
| Electron | 生态最成熟，但 150MB+、内存高 | ★★☆ 与哲学冲突 |
| Fyne/Gio | Go 原生但富文本/PDF 弱 | ★★★☆ 专利文档场景吃力 |

设计文档的对比表格准确。尤其 Mady 后端已是 Go、且已有 `server.Handler()`，Wails 内嵌避免了 Tauri/Electron 必需的 sidecar + JSON IPC，这是关键差异点。

**建议**：在 03-design.md 中补充 Wails v2.12.x 的版本锁定说明（开源项目 `safetyculture-exporter` 的 CLAUDE.md 指出 v2.12.0 修复了 clipboard、WebView stability、Linux panics，且 Vite 兼容性更稳）。

### 3.2 前端栈：React 18 + shadcn/ui + Tailwind v4 + Motion 合理

开源社区同类项目（nexus-ai、jean、Beadbox、mp4-optimizer）普遍采用：

- React 19/18 + TypeScript
- Tailwind CSS v4 + shadcn/ui
- Zustand + TanStack Query
- Vite

这与本设计完全一致。React 作为 A2UI 声明式 UI 的宿主是事实标准（CopilotKit、a2ui-react-runtime 均基于此），shadcn/ui 的“复制粘贴可定制”哲学也与 Mady 的克制定位一致。

**需要注意的版本兼容性**：
- Wails v2 对 Vite 7+ 的 dev server 曾有兼容问题（Wails issue #4620），建议锁定 **Vite 5.4.x**；
- Tailwind v4 的 `@theme` 指令与 Wails embed 的 CSS 输出需验证；
- React 18 与 Wails v2 默认模板兼容，但升级到 React 19 需确认 Wails 的 TypeScript 绑定生成工具。

### 3.3 A2UI 渲染器：方向正确，但需细化 4 处

A2UI 渲染器确实是“写一次，多端复用”的核心资产。开源参考：

- **CopilotKit** 的 `createA2UIMessageRenderer`：theme-driven，组件映射到 shadcn/ui；
- **a2ui-react-runtime**：分为 `MessageProcessor`、`Renderer`、`Theme` 三层；
- **a2ui-blazor**：`SurfaceManager` + `<A2UISurface>` 组件。

本设计的 `SurfaceStore` + `renderer.tsx` + `dynamic.ts` + `theme/tokens.ts` 四层划分合理。

**需细化的问题**：

1. **Dynamic 的 wire 格式不一致**：Go 端 `a2ui.Dynamic` 序列化为：
   - 字面量：直接值（如 `"hello"` / `42`）
   - 绑定：`{"path": "/user/name"}`
   - 函数调用：`{"call": "formatString", "args": {...}}`

   但 02-spec.md §3.3 描述为 `{ literal: T }` / `{ bind: ... }` / `{ function: ..., args: [...] }`，与实现不符。前端若按 spec 实现会解析失败。

2. **自定义 catalog 支持**：Mady 专利领域可能有自定义组件（如 `ConclusionCard`、`ConfidenceBar`、`ApprovalCard`）， spec 仅覆盖 BasicCatalog 18 组件。建议明确“业务组件”与“A2UI Basic 组件”的边界：业务组件放在 `frontend/src/components/`，A2UI Basic 组件放在 `frontend/src/a2ui-renderer/components/`。

3. **Component 字段结构**：需确认 Go 端 `a2ui.Component` 的 JSON 形状（props 是 `map[string]any`），前端 TS 类型要与 Go 端 1:1。

4. **SurfaceStore.dataModel 的不可变更新**：spec §3.3 提到 memoize `bind` 结果，但若 dataModel 是 mutable object，WeakMap 缓存会失效。建议强制不可变更新（ immer / structuredClone 小片更新）。

### 3.4 事件透传：Wails Events 优于 EventSource，但映射层被低估

设计文档选择 Wails Events 而非 WebView 原生 EventSource 是正确的：

- WKWebView 对 `text/event-stream` 有已知 buffering 问题；
- Wails Events 是同进程 IPC，无跨域/混合内容限制；
- 开源 Wails 官方指南也推荐用 namespaced events（如 `agui:message-delta`）。

**但实现细节需澄清**：

1. `agui.Converter` 输出的是标准 `agui.EventType`（如 `RUN_STARTED`、`TEXT_MESSAGE_CONTENT`、`CUSTOM`），不是 `agui:agent-start`。桌面端需要在 `App.startup` 里做一层映射，并处理 `CustomEvent.Name`（如 `handoff_start`、`a2ui`、`approval_prompt`）。

2. `agui:done` 事件在 `agui.Converter` 中不存在。当前 `server/chat.go` 的 `StreamDoneEvent` 是 HTTP SSE 层自定义的。桌面端需要在 chat 完成后自行 emit `agui:done`。

3. 一次 `agentcore.Event` 经 `agui.Convert` 可能产生多个 AGUI 事件（如 `AgentEndEvent` → `closeAll + RunFinishedWithSuccess`），需要循环 `runtime.EventsEmit`。

4. 当前 `server.handleStreamChat` 的事件监听注册在 **agent 自己的事件总线**（`agent.OnAll`）上，而不是 `server.eventBus`。因此桌面端若仅订阅 `srv.OnAll()` 会**收不到 chat 消息**。这是最大的实现缺口。

### 3.5 设计系统：Apple HIG + 语义 token 专业且可落地

设计文档的配色、字体、材质、动画规范详尽，与 Apple HIG 对齐，符合专利/法律专业工具“可信、精致”的气质。

**亮点**：
- 主 accent 用 `systemIndigo` 呼应图标深紫，橙色仅作品牌点缀；
- 语义 token 自动适配 light/dark/高对比；
- 动画 ≤250ms、尊重 `prefers-reduced-motion`；
- 与 TUI theme 的语义映射表保留品牌一致性。

**建议**：
- 在 `frontend/src/theme/tokens.ts` 中同时输出 CSS 变量和 Tailwind v4 的 `@theme` 定义，便于 shadcn/ui 组件消费；
- 深色模式下专利文档区使用略暖白色，这个细节很好，但需在 CSS 中显式定义；
- SF Symbols 不能跨平台分发，建议默认使用 Lucide React，仅在 macOS 运行时通过 Wails 注入的 platform 信息决定是否使用 SF Symbols。

### 3.6 安全与 Handoff 契约：考虑充分

- Invisible Handoff 前端静默、过滤 `transfer_to_*` 工具调用，符合 `domains/unified.go` 的统一 Agent 契约；
- openUrl 仅允许 http(s)，防止 `javascript:` / `file:` 协议；
- API Key 不泄露到前端，调试端口仅 dev 开启；
- Wails Binding 不暴露文件系统/exec。

**补充建议**：
- A2UI 渲染器必须禁用 `dangerouslySetInnerHTML` 和 `eval`；
- 前端对 A2UI envelope 做结构校验时，防止 oversized payload 导致渲染卡顿；
- Wails 的 `TitleBarHiddenInsetUnified` 虽美观，但需确保窗口控制按钮（红绿黄）不与 UI 元素重叠。

## 4. 与现有代码的匹配度：具体缺口

| # | 设计文档假设 | 现有代码现实 | 影响 | 建议处理 |
|---|-------------|-------------|------|----------|
| 1 | `App.Chat(req)` 复用 `server.handleChat` | `handleChat` 是私有方法，且事件监听在 `agent.OnAll` | 高（阻塞） | 新增 `Server.Chat(ctx, req, onEvent)` 公开方法；或让 desktop 直接构造 agent |
| 2 | 复用 `cmd/mady` 的 `setupFrameworkContext` | 函数未导出，且位于 `package main` | 高（阻塞） | 提取到 `pkg/framework` 或 `internal/framework`，去掉 `os.Exit` |
| 3 | `a2ui.Dynamic` 格式为 `{bind}/{literal}/{function}` | 实际为 `{"path":...}` / 字面量 / `{"call":...}` | 高（实现错误） | 修正 spec，前端按实际格式解析 |
| 4 | `agui.Converter` 直接产出 `agui:*` 事件名 | 产出 `RUN_STARTED` 等标准 AGUI 类型 | 中 | 在 desktop/app.go 增加事件名映射层 |
| 5 | 桌面端通过 `srv.OnAll()` 接收 chat 事件 | chat 事件在 agent 总线，`srv.OnAll` 监听 server 总线 | 高（阻塞） | 与 #1 一起解决：chat 方法暴露事件回调 |
| 6 | `App.Cancel(runId)` / `SendAction` / `Health` | `Server` 无这些方法 | 中 | 新增或让 desktop 直接访问 agent/session |
| 7 | `agui:done` 事件 | `agui.Converter` 不产出 done | 中 | 桌面端 chat 方法结束时 emit |
| 8 | `ListThreads/GetThread/DeleteThread` | 只有 HTTP handlers，无公开方法 | 中 | 新增 `Server` 封装方法，或 desktop 直接操作 threadStore |
| 9 | Wails Events 单 payload | 一次 Convert 可能产生多事件 | 低 | 循环 emit，已自然满足 |
| 10 | `desktop/go.mod` 引入 Wails | 可能与根模块的 `golang.org/x/sys`、`golang.org/x/net` 等版本冲突 | 中 | 首次 `go.work sync` 时检查并 pin |
| 11 | Tailwind v4 + Vite 8 | Wails v2 对 Vite 7+ dev server 曾有兼容问题 | 中 | 锁定 Vite 5.4.x，生产构建验证 |
| 12 | Playwright e2e 测试 WebView | WebView 自动化难度大 | 低 | 优先用 Wails 测试模式 + mock runtime；Playwright 作为阶段 3 增强 |

## 5. 开源社区优秀实践对照

### 5.1 桌面 AI 应用架构

- **nexus-ai**（Tauri v2 + React 19 + shadcn/ui v4 + Zustand v5 + TanStack Query v5）：验证了同技术栈的可行性，其 `src/services/` 层封装 LLM/MCP 调用，与本设计的 `agui-bridge/` 类似。
- **jean**（Tauri v2 + React 19 + Tailwind v4 + shadcn/ui + Zustand + TanStack Query）：多项目、多会话、终端集成，展示了专业开发者工具的 UX 复杂度。
- **Beadbox**（Tauri v2 + Next.js 16 + shadcn/ui + Tailwind v4）：证明了 shadcn/ui 可支撑完整的 issue tracker 级桌面 UI，但 160MB 体积提醒我们避免 bundling Node.js sidecar。

**Mady 的差异化优势**：选择 Wails + Go 内嵌，天然避免 sidecar 和 Node.js runtime，二进制可控制在 15-25MB。

### 5.2 A2UI 渲染器实现

- **CopilotKit** 的 `createA2UIMessageRenderer`：theme-driven，强调“组件注册表 + theme”而非硬编码组件；
- **a2ui-react-runtime**：`MessageProcessor` 处理 data binding 和 envelope dispatch，`Renderer` 只做组件映射；
- **a2ui-blazor**：`SurfaceManager` 维护 surface 集合，`<A2UISurface>` 按 ID 渲染。

**建议 Mady 采用的分层**：

```
a2ui-renderer/
├── catalog.ts          # CatalogRegistry + BasicCatalog 定义
├── store.ts            # SurfaceStore（处理 envelope、data model）
├── dynamic.ts          # Dynamic / Bind / FunctionCall 解析
├── renderer.tsx        # 组件分派 + 树渲染
├── registry.tsx        # ComponentType → ReactComponent 映射
├── theme.ts            # 将 A2UI theme properties 映射到 Tailwind class
└── components/         # 18 个 Basic 组件实现
```

这样与开源 renderer 结构一致，也便于未来抽成独立 npm 包。

### 5.3 流式 UI 最佳实践

- **CSS containment**：长对话中给 message bubble 加 `content-visibility: auto`，可减少 40-60% 渲染时间；
- **MessageBubble memo**：仅当前流式消息 re-render；
- **AbortController**：用户点击停止时，取消后端流并释放资源；
- **Token batching**：每 16ms 合并一次 token，避免每字 render。

设计文档已在 §7 性能考量中补充 CSS containment 和 `MessageBubble` memo 策略。

### 5.4 工程化与 CI

开源 Wails + React 模板（Mahcks/wails-vite-react-tailwind-shadcnui-ts）通常提供：
- `wails dev` / `wails build` 脚本
- 跨平台 build scripts
- 自动 embed frontend/dist

Mady 的 Makefile 集成思路正确，但需确保：
- `make desktop-run` 先 `cd desktop/frontend && pnpm build`；
- CI 上 macOS runner 安装 Wails CLI 和 Node/pnpm；
- 对 `desktop/` 模块单独跑 `go build ./...`，不依赖根模块的 `go build ./...`。

## 6. 风险与建议

### 6.1 高风险

| 风险 | 说明 | 缓解 |
|------|------|------|
| **Chat 事件无法被 server 总线捕获** | `server.handleStreamChat` 监听 `agent.OnAll`，`srv.OnAll` 是 server 总线 | 新增 `Server.Chat(ctx, req, onEvent)`，在方法内部注册 `agent.OnAll` 回调 |
| **框架装配函数不可复用** | `setupFrameworkContext` 在 `cmd/mady` 的 main 包中未导出 | 提取为 `pkg/framework.Setup(ctx, opts)`，返回 `BaseConfig` + `MadyHome` + 可选 deferred |
| **A2UI Dynamic 格式漂移** | Spec 描述与 Go 实现不一致 | 开工前修正 spec，并添加 Go ↔ TS 对照测试 |
| **Wails v2 与 Go 1.26 兼容性** | Wails v2 支持 Go 1.21+，但 Go 1.26 较新 | T1.1 先用 `go mod tidy` 验证，必要时临时降级到 1.24 |

### 6.2 中风险

| 风险 | 说明 | 缓解 |
|------|------|------|
| Vite/Tailwind v4 与 Wails v2 dev server 兼容性 | 开源经验显示 Vite 7+ 曾破坏 Wails dev server | 锁定 Vite 5.4.x + `@tailwindcss/vite` 插件 |
| AGUI 事件名映射遗漏 | `CustomEvent` 的 name 需映射为 kebab-case | 在 desktop/app.go 中集中维护映射表，并加单测 |
| A2UI 渲染器工作量被低估 | 18 组件 + 15 函数 + data model + 验证 | T2.3 只做 P0（9 组件），其余后置 |
| 多模块依赖冲突 | `desktop` 引入 Wails 后可能影响根模块依赖图 | `go.work sync` + `go mod tidy` 后 diff 检查 |

### 6.3 低风险

- 前端依赖体积：通过 `pnpm` 和 `vite build` tree-shake 可控；
- WKWebView 渲染差异：避免 bleeding-edge CSS，用 Tailwind 默认值；
- 签名/公证：阶段 3 用 ad-hoc 签名，不阻塞 MVP。

## 8. 结论

Mady 桌面端设计文档是一份**高起点、细节足、方向对**的规格，具备落地的可行性。它准确识别了“协议资产已到临界点”“A2UI 渲染器是核心资产”“macOS 原生专业工具美学”等关键成功要素。

但设计文档目前处于“理想接口”与“现有实现”之间存在 4 处关键落差的阶段。建议在正式开工前：

1. 先完成 B1-B4 阻塞项的修正；
2. 用最小原型（T1.1 + T1.2 + T1.5 的简化版）验证事件透传路径；
3. 明确 `pkg/framework` 的提取方案，并同步调整 `mady serve` / `mady tui` 入口复用该包；
4. 锁定前端工具链版本，避免在 Wails v2 兼容性上返工。

完成以上修正后，阶段 1-3 的任务拆解可按计划推进，预计能如期产出 macOS MVP。
