**背景**：仓库此前零工程 issue——累计的全部技术债务只存在于 `docs/` 的审计报告里，
无负责人、无状态流转、无跨版本追踪。且经回代码核验，`docs/` 中 6 条 P0 有 5 条
已实际修复但文档仍标记未修复——文档作为唯一事实源已不可信。

本次完成「债务 → issue」的首次关联，并**同时建立防漂移机制**，否则映射半年后
会与旧文档同样失效。

**改动清单**：

- `docs/plans/debt-issue-map.md`（新增）—— 债务 ↔ issue 映射报告：P0–P3 全量 61 条、
  调研方法与逐条核验结论、分批创建方案、风险与执行顺序。
- `docs/plans/debt-issues.json`（新增）—— DEBT 编号 ↔ issue 映射的**唯一事实源**。

**核验结论（推翻文档旧结论的部分）**：

- `docs/` 中 6 条 P0，**5 条已修复而文档未回写**：AGUI RUN_ERROR（已发射）、
  pregel 裸 map 合并（已有 `sort.Strings` 确定性）、`pipeline_executor.go`
  （文件已不存在）、goroutine panic 隔离（三处均有 `recover()`）、deferred_persist
  队列（已接线 `assemble.go:122` + `levels.go:138`）。
- 唯一真实 P0 隐私项被**两个方向同时误判**：旧报告称「25 条路径全部未脱敏」（错，
  主链路已接线），而若采信「已修复」又会漏掉 desktop 全域与 TUI provider 切换点
  至今零脱敏（DEBT-01）。
- 核验中另发现**替代问题**：`graph/pregel.go:294-299` 的 `recover()` 不写入 `errs`，
  而 `:322-326` 仅遍历 `errs` 判失败——panic 被静默吞掉，图返回看似成功的残缺结果
  （DEBT-05），比原文档「panic 无隔离」的描述更隐蔽。

**编号治理**：核验中发现 `DEBT-06` 被同时分配给 P1 条目与 §9.4 已知限制条目，
已改派后者为 `DEBT-57`，并在报告中固化「编号一经分配不得复用」规则；
`debtlink` 启动时即拒绝重复编号。

**独立审查修复**：交付前经独立 code-review，修掉 3 处「该失败却通过」的假阴性——

1. **规则 1 恒不触发**：正文登记校验原本扫描整篇文档，而索引区块由本工具生成、
   必然列出全部编号，故只要跑过一次 `-apply`，未在正文登记的债务也会被判为已提及。
   现已用 `stripBlock` 剔除区块后再扫描。
2. **规则 1/2 在降级态下形同虚设**：报告缺标记时 `inDoc` 为空 map，既把「缺标记」
   误报成「所有条目正文登记缺失」（61 条噪音），又让幽灵编号检测失效——实测报告里
   明写着 `DEBT-99` 却不报。现结构错误时短路，只报一条并跳过覆盖性检查。
3. **元数据无校验**：`issue: 5, status: ""` 会渲染成「#5 + 待建」的自相矛盾行、
   `repo` 写错静默产出坏链接、`issue: 0/-7` 产出无效链接，而 check 4 只看
   `open`/`pending` 两分支，均判为通过。现由 `loadSource` 收紧为闭集/格式校验。

另修正：`-gh` 不再把期望状态写死 `OPEN`（否则正常关闭 issue 并同步事实源后会被判失败）、
成功文案不再在未核验时宣称「与 GitHub 一致」、单元格转义补反斜杠与换行（原实现会把
`\|` 二次转义成裸管道、标题含换行会断表）。

**验证**：

- `make lint` → 0 issues（含新增脚本）；`gofmt` 干净
- `go test ./scripts/debtlink/` → 21/21 通过（34 含子测试）
- 负控制自测均 fail-closed：幽灵编号、索引过期、字段缺失、状态矛盾、编号重复、
  元数据非法、缺索引区块、`-apply`+`-check` 同给
- 端到端复验规则 1：把幽灵条目写进事实源并 `-apply`（区块因此含该编号）→ `-check`
  正确报「报告正文未提及」；修复前此路径静默通过
- `make build` / `make doc-check` / `make check-arch` / `make debt-check` 全绿

**影响**：债务首次进入 issue 跟踪体系，可指派、可流转、可被外部贡献者看见。
新增 `make verify` 门禁项 `debt-check`——后续新增债务若只改报告不改事实源，
CI 会直接失败，从机制上阻断文档二次腐化。
